# 学习平台本地读写压测报告（2026-11-15）

## 1. 测试概述

本次为本机 Windows + Docker Desktop 的 loopback 压测，目标是拿到学习平台（Go 1.27 / go-zero 单实例）的真实并发上限，并与同日 VideoNest（Java 21 / Spring Boot 4.1）做同口径对照。

| 项目 | 内容 |
|------|------|
| 测试时间 | 2026-11-15 |
| 宿主机 | Intel i7-13700H，14 核 20 线程，15.6 GB 内存 |
| Docker 资源 | 7.57 GB 内存，无 CPU 配额限制 |
| 目标入口 | `http://127.0.0.1:8888`（learningplatform-backend 直连，不经 Nginx） |
| 应用栈 | go-zero 1.10 单进程；MySQL 8.4（go-zero sqlx 默认连接池 64）；Redis 7；MongoDB 7；MinIO；ai-service |
| 发压工具 | `load-test/2026-11-15/bench.js`（与 VideoNest 同一份 Node 22 原生 http 发压器） |
| 并发阶梯 | 读 8 / 16 / 32 / 64，写 4 / 8 / 16，混合 16 / 32，每档 20 秒 |
| 预热 | 每轮 8 秒预热（8 并发，不采集） |
| 隔离条件 | 测试期间 VideoNest 整套容器已停止，宿主机只跑学习平台栈 + 发压进程 |

## 2. 数据夹具与前置修复

本地库原本是空课程列表（0 条课程），直接压空列表没有意义，因此按业务表结构灌入可清理的压测样本：

- 24 门课程 `LPBENCH_01..24`，每门 3 个视频，共 72 条 `course_videos`，`process_status=done`。
- 班级 1 绑定其中 6 门课程；把 4 个探针账号加入班级 `class_members`（学生角色），否则班级相关接口返回 403。
- 4 个探针账号 `lpbench_1..4`，用 `/api/user/register` + `/api/user/login` 取 token。
- 灌数据后对 Redis `course:list:ver` 做版本号递增，避免命中旧的空列表缓存。

## 3. 读场景结果（混合 5 类读接口）

权重：课程列表 30%、课程详情 25%、公告列表 20%、作业列表 15%、班级详情 10%（后三者带 JWT）。

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 8 | 2466.06 | 3.17 ms | 5.00 ms | 6.09 ms | 100% |
| 16 | 3071.91 | 5.11 ms | 7.81 ms | 9.32 ms | 100% |
| 32 | 2855.63 | 11.16 ms | 16.13 ms | 19.59 ms | 100% |
| 64 | 2510.80 | 25.76 ms | 29.39 ms | 32.08 ms | 100% |

分接口（32 并发，QPS 为该场景分摊值）：

| 接口 | QPS | P95 |
|------|-----|-----|
| 课程列表 `/api/course/list` | 851.55 | 12.55 ms |
| 课程详情 `/api/course/detail/{id}` | 718.98 | 15.28 ms |
| 公告列表 `/api/class/1/announcements` | 567.17 | 18.52 ms |
| 作业列表 `/api/class/1/assignments` | 432.70 | 14.95 ms |
| 班级详情 `/api/class/1` | 285.23 | 15.94 ms |

结论：读峰值在 16 并发达到 3072 QPS，32 并发已回落 7%，64 并发回落 18%，拐点比 VideoNest 更早（16 而非 32）。但尾延迟控制更好：64 并发 P95 只有 29.4 ms、P99 32.1 ms，VideoNest 同点是 43.6 / 55.6 ms。也就是说 Go 侧“峰值来得早、跌得缓、尾巴短”，Java 侧“峰值更高、扛得更久、尾巴更长”。

## 4. 写场景结果

### 4.1 新增笔记 `POST /api/course/note`（MySQL 插入）

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 4 | 652.49 | 5.58 ms | 8.84 ms | 18.89 ms | 100% |
| 8 | 937.76 | 7.43 ms | 17.48 ms | 22.48 ms | 100% |
| 16 | 1226.89 | 10.77 ms | 24.15 ms | 29.03 ms | 100% |

### 4.2 保存播放进度 `POST /api/course/video/progress/{cid}/{vid}`（MySQL upsert + Redis）

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 4 | 509.78 | 6.95 ms | 14.14 ms | 22.68 ms | 100% |
| 8 | 634.49 | 10.76 ms | 24.99 ms | 32.69 ms | 100% |
| 16 | 821.04 | 17.20 ms | 35.60 ms | 50.98 ms | 100% |

结论：写路径没有限流，QPS 随并发线性上升到 16 并发仍在涨（笔记 1227、进度 821），但 P95 已翻倍，说明单行写开始排队。进度写入比笔记更慢，因为它同时维护 Redis 累计观看秒数与 MySQL 进度行，属于双写路径。

## 5. 读写混合场景（读 5 类 + 笔记写，约 20% 写）

| 并发 | QPS | P50 | P95 | P99 | 成功率 |
|------|-----|-----|-----|-----|--------|
| 16 | 2125.84 | 6.90 ms | 12.99 ms | 15.52 ms | 100% |
| 32 | 2321.43 | 13.46 ms | 19.78 ms | 22.70 ms | 100% |

混合场景吞吐随并发继续上升到 2321 QPS，没有出现 VideoNest 那种 16 并发即封顶的形态，说明 go-zero 在读写争抢下仍有调度余量；但混合 P95（19.8 ms）高于纯读（16.1 ms），写入确实在拖尾。

## 6. 瓶颈判断

- 读峰值早于 Java：16 并发即 3072 QPS，之后下降。go-zero 路由与 JSON 序列化很轻，但单进程 GOMAXPROCS 调度在 64 并发时报文处理出现排队，P50 从 5.1 ms 涨到 25.8 ms 就是证据。
- 写路径没有保护层，QPS 线性增长但尾延迟同步放大，16 并发 P99 已达 51 ms（进度写）。生产上需要在前端或网关加写限流/合并，否则突发写入会直接打到 MySQL。
- 班级详情（285 QPS）是最慢读接口，明显低于课程列表（852），说明它做了多次关联查询（成员、课程、公告等），是可优化点。
- 未采集容器级 CPU 采样，本报告不声称 CPU 已打满，结论基于吞吐与延迟曲线。

## 7. 优化建议

1. 班级详情做聚合查询或加 Redis 缓存（成员数、课程数变化不频繁），预计能把 285 QPS 拉到 600+。
2. 播放进度写入可按用户+视频做 1 秒节流/合并，前端本来就高频上报，合并后能显著降低双写压力。
3. 读路径在 32 并发后回落，建议确认 GOMAXPROCS 与容器 CPU 配额是否匹配，并压测 48 并发找更细的拐点。
4. 与 VideoNest 相比，学习平台缺少写限流层，建议补一个按用户维度的令牌桶，避免异常客户端刷写接口。

## 8. 复现方式

```bash
node load-test/2026-11-15/bootstrap.js load-test/2026-11-15/tokens.json lpbench \
  http://127.0.0.1:8888 /api/user/register /api/user/login

node load-test/2026-11-15/bench.js --config=load-test/2026-11-15/scenarios.json \
  --out=load-test/2026-11-15/raw --label=read --suite=read --secs=20 --ladder=8,16,32,64
```

写场景 `--suite=write --scenario=note-create`（或 `progress-save`），阶梯 `4,8,16`。样本数据由 `seed.sql` 灌入。
