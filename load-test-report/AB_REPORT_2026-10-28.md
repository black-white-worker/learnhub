# 并发/查询优化 A/B 压测报告

**日期**：2026-10-28
**目的**：验证本轮 B 端并发与查询优化在 HTTP 链路上的实际收益（优化前 vs 优化后）。
**结论**：公告列表与成绩册是两个数量级差异最明显的接口；视频进度写、班级详情、列表分页也有稳定提升，全部请求 0 错误。

---

## 1. 环境与方法

| 项 | 说明 |
|---|---|
| 机器 | 同一台 Windows 笔记本，压测期间不跑其他业务 |
| 后端 | 同一份代码构建两个二进制：`before`（旧实现）与 `after`（本轮优化后） |
| 数据库 | 本机 MySQL 9.6，两个独立库：`lp_bench_before` 只应用 V1–V21；`lp_bench_after` 应用 V1–V22 |
| 缓存 | miniredis（内存 Redis），两个后端共用，避免 Docker 依赖 |
| 数据 | 两库完全一致：1 个班 121 名成员、30 份作业 + 8 场考试（4560 条成绩）、40 次签到（3840 条记录）、4 门课 48 个视频（3456 条进度）、20 条公告（1440 条已读）、12000 条通知 |
| 客户端 | 自写 Go 压测器（固定并发、闭源模型、预热 1s、丢弃预热数据），仅标准库 |
| 场景 | 公告列表、成绩册、班级详情、视频进度写、作业列表、通知列表 |
| 参数 | 读接口 50 并发 × 6s；成绩册 30 并发 × 8s；进度写 20 并发 × 6s |
| 轮次 | 两轮，第二轮把执行顺序完全反过来（after 先跑），用于抵消机器预热/顺序偏差 |
| 错误率 | 两轮、两侧全部 0 失败（HTTP 200） |

> `before` 与 `after` 只差本轮改动：公告批量聚合、成绩册预聚合、视频进度少一次回读、
> 班级详情 4 路有界并发、会话携带 userId、V22 的 7 个索引。后台自动收卷与业务无关，
> 压测前已把"考试中"答卷置为已提交，避免后台写负载干扰。

## 2. 结果（第二轮，顺序反转）

| 接口 | before QPS | after QPS | QPS 提升 | before P95 | after P95 |
|---|---:|---:|---:|---:|---:|
| 公告列表 | 303.2 | **1242.3** | **+310%** | 261.3ms | **67.6ms** |
| 成绩册 | 25.3 | **72.0** | **+185%** | 1239.8ms | **485.7ms** |
| 视频进度写 | 1320.3 | **1908.2** | **+45%** | 19.4ms | **13.9ms** |
| 作业列表 | 1542.9 | 1816.6 | +18% | 56.9ms | 49.3ms |
| 通知列表 | 1958.7 | 2482.0 | +27% | 41.0ms | 32.4ms |
| 班级详情 | 900.9 | 987.9 | +10% | 93.2ms | 85.0ms |

第一轮（正序）与第二轮方向一致，QPS 比值分别为：
公告 **4.5×** / 成绩册 **2.9×** / 进度写 **1.5×** / 作业 **1.2×** / 通知 **1.3×** / 班级详情 **1.07×**。
说明收益不是单次抖动。

**分位延迟（第二轮，before → after）**

- 公告列表：P50 157.4 → 37.7ms，P99 316.7 → 86.6ms
- 成绩册：P50 1180.2 → 409.7ms，P99 1252.0 → 571.1ms
- 视频进度写：P50 14.8 → 10.1ms，P99 23.1 → 17.4ms

## 3. 怎么解释这些数字

- **公告列表（4.1×）**：旧实现每条公告一次 `announcement_reads` 查询（20 条约 21 次 SQL），
  还用 8 路 `errgroup` 并发掩盖；新实现一条 `GROUP BY` 算完整页，固定 2 条 SQL。
  QPS 从 303 涨到 1242，P95 从 261ms 降到 68ms，说明瓶颈就是 N+1 与并发争抢。
- **成绩册（2.85×）**：4 个相关子查询对每个学生执行一次，改成"预聚合 + LEFT JOIN"，
  视频段用 `STRAIGHT_JOIN` + 覆盖索引；P95 从 1.24s 降到 486ms。这是单请求最重的接口，
  也是这次收益绝对值最大的接口。
- **视频进度写（1.45×）**：读 → 写 → 再读（3 次往返）改为读 → 写（2 次），
  纯函数在内存里算完直接返回；这是最高频写路径，QPS 上限随连接池占用下降而抬高。
- **作业列表 / 通知列表（+18% / +27%）**：代码逻辑没改，收益来自 V22 索引
  （`(class_id, created_at)`、`(user_id, id)`），分页不再 filesort。
- **班级详情（+10%）**：4 段查询从串行改为 4 路有界并发；本机 RTT 很小，
  所以提升有限，远程数据库/跨机房时收益更大。

## 4. 可信度与局限

- 数据是合成数据（120 人规模），**不是生产数据分布**；结论用于判断方向与数量级，
  不能直接作为容量规划依据。
- 单机 MySQL + 内存 Redis，网络 RTT 接近 0；生产环境 RTT 更高，批量查询与少往返的收益会**更大**，
  而不是更小。
- 每轮 6–8 秒，未覆盖 30 分钟长稳、GC 与连接池耗尽；P99 在小样本下会有抖动。
- "作业列表"不是纯对照组：它同样受 V22 索引影响，因此不能把 +18% 全算作噪声。
- 两个后端共用同一 MySQL 实例，压测是顺序执行的，未测试同时混合读写。

## 5. 复现方式

1. 建两个库，分别应用 `backend/deploy/sql/migration/V1–V21`（before）与 `V1–V22`（after）；
2. 两库都导入 `scripts/perf/seed_gradebook_bench.sql`；
3. 用同一份代码构建 `after`，把本轮改动的文件回退后构建 `before`；
4. 起本地 Redis（或 miniredis），两个后端分别连各自库、监听不同端口；
5. 登录拿 token，按上面的并发/时长打接口，采集 QPS 与分位延迟。

业务 SQL 的对照（旧/新成绩册各 121 行结果逐行一致、EXPLAIN ANALYZE 前后对比）
见 `docs/performance.md` §3 与 `backend/internal/model/query_integration_test.go`。
