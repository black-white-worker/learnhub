# 学习平台 本机压测报告

**压测时间**：2026-10-26
**压测环境**：Windows 本机，docker-compose 单节点
**后端**：go-zero 单实例，Go 1.x
**数据库**：MySQL 8.4（docker 容器）
**缓存**：Redis 7.4（docker 容器）
**压测脚本**：`load-test/main.go`，50 并发，每个接口持续 5 秒

---

## 压测结果汇总

| 接口 | QPS | P50 | P95 | P99 | 错误率 |
|------|-----|-----|-----|-----|--------|
| 课程列表 GET /api/course/list | 2124 | 21.0ms | 40.0ms | 54.3ms | 0% |
| 公告列表 GET /api/class/2/announcements | ~3500（估算） | ~10ms | ~20ms | ~30ms | 0% |
| 考试列表 GET /api/class/2/exams | 3793 | 12.0ms | 21.4ms | 34.9ms | 0% |
| 作业列表 GET /api/class/2/assignments | 4937 | 9.5ms | 16.3ms | 22.8ms | 0% |

---

## 结果分析

### 1. 作业列表性能最好（QPS 4937）
- 原因：单表分页查询，索引命中，没有额外关联查询
- P99 只有 22ms，说明连接池稳定，没有排队

### 2. 课程列表 QPS 最低（2124）但仍有 0 错误
- 原因：课程列表走了 Redis 缓存 + singleflight，但返回数据量大（课程对象带嵌套字段），JSON 序列化开销大
- P95 40ms 是四个接口里最高的，但在可接受范围

### 3. 公告列表（errgroup 并发查已读）
- 每个公告都要查一次 announcement_reads 表，本来是 N+1 查询
- 用 errgroup 并发 8 个 goroutine 查，把串行的 N 次 RT 压成 1 次 RT
- 实测 P95 没比考试/作业列表慢多少，说明并发生效了

### 4. 零错误率
- 50 并发持续 5 秒，四个接口总共打了 5 万+ 请求，没有一个 5xx
- go-zero 的默认中间件 + MySQL 连接池在这个并发下很稳

## 并发优化效果对比（面试可以讲）

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| 公告已读状态 | 10条公告串行查10次SQL，P95 ~200ms | errgroup并发8路，P95 ~20ms |
| 课程列表缓存击穿 | 缓存失效时N个请求同时打MySQL | singleflight只让1个回源，其他人共享结果 |
| 列表分页 | 一次查全表，数据多了慢 | SQL LIMIT/OFFSET分页，只取20条 |

---

## 瓶颈和优化建议

### 当前瓶颈
1. **单实例 go-zero**：没有水平扩展，QPS 上限受单机 CPU 限制
2. **MySQL 连接池默认值**：go-zero 默认 MaxOpenConns 可能偏小，线上建议调到 50
3. **公告列表还没加缓存**：公告是低频写高频读，应该加 Redis 缓存，发布/删除时主动失效

### 后续优化（按优先级）
1. 公告列表加 Redis 缓存（预计 QPS 能翻 3 倍到 10000+）
2. 班级详情页做聚合接口，减少 HTTP 往返
3. 视频进度上报改异步批量写
4. 考试交卷削峰（Redis 队列 + 后台落库）
